大型專案管理:以 Git 為例

貓貓冊店專欄 ・ 一個人寫的程式,和一千個人寫的程式,是兩種完全不同的問題

您一定看過這樣的檔案名稱:「報告.docx」「報告_修改版.docx」「報告_最終版.docx」「報告_最終版_真的最後.docx」。這就是最原始的「版本管理」,而它在三個人以上就會開始失控。

軟體專案比寫報告複雜得多:程式動輒幾十萬行,幾十、幾百甚至上千人同時修改,而且改錯一行,整個系統可能就掛了。這篇文章想說明:大型專案真正難在哪裡?以及一套叫做 Git 的工具,是怎麼一一回答這些難題的。

一、大型專案難在哪?三個核心難題

  • 記憶:一年前,是誰、為什麼把這一行改成這樣?出了問題,能不能退回到昨天好好的狀態?
  • 平行:十個人同時要改同一個系統,怎麼讓大家各做各的,互不踩到對方?
  • 整合與品質:大家的改動合在一起之後,還能正常運作嗎?誰來確認?

1975 年,軟體工程師佛瑞德・布魯克斯(Fred Brooks)在《人月神話》裡提出一個著名的觀察:在已經延遲的軟體專案裡增加人手,只會讓它更晚完成(布魯克斯法則)。原因是人越多,彼此溝通與協調的成本就增加得越快。所以大型專案管理的重點,從來不是「讓大家寫得更快」,而是「讓協作的成本降下來」。

二、Git 從哪裡來?

Git 由林納斯・托瓦茲(Linus Torvalds)在 2005 年創造,他也是 Linux 作業系統核心的創始人。當時 Linux 核心的開發者使用一套叫做 BitKeeper 的商業版本控制軟體,後來 Linux 社群與該公司的關係破裂,免費使用的權利被收回,於是托瓦茲決定自己寫一套。

Git 最大的特色是分散式:每個開發者的電腦上,都有一份完整的專案歷史。沒有網路也能提交、查歷史、開分支;不會因為中央伺服器壞了,整個專案就沒救。

三、先看懂 Git 的世界:三個地方

剛學 Git 的人最容易卡在一件事:為什麼存個檔要「兩個步驟」?因為 Git 把您的檔案分成三個地方。可以想像成寄一個包裹:

下面是會一直出現的幾個名詞,先看一眼就好,後面的圖與範例會讓它們變得具體:

名詞白話意思
倉庫(repository)存放專案與「完整歷史」的地方,在您的資料夾裡是一個隱藏的 .git 資料夾
提交(commit)替專案在某一刻拍的一張快照,附上說明
分支(branch)一條可以獨立發展的路線(其實只是貼在某個提交上的標籤)
合併(merge)把兩條路線的改動合在一起
衝突(conflict)兩邊改了同一個地方,Git 不敢替您決定,需要人來選

四、Git 如何回答三個難題

(一)記憶:提交(commit)與歷史

在 Git 裡,每一次「提交」(commit),就是替整個專案在那一刻拍一張快照,並附上作者、時間,以及一段說明。每個提交都記得自己的「上一個」是誰,所以整個專案的歷史,就是一條可以一路往回追的鏈。每個提交還有一組獨一無二的雜湊值(很長的一串英數字)當作身分證。

  • 提交說明要寫「為什麼」:「修正登入失敗」比「改了東西」有用得多。一年後的您,會感謝現在寫清楚的自己。
  • 安全地回到過去:想撤銷某個改動,可以用 revert,它會新增一個提交去抵銷舊的,歷史不會被改寫,對團隊最安全(下圖對比了 revert 與危險的 reset)。
  • 追查問題來源:blame 可以看到每一行最後是誰、在哪次提交改的;bisect 則用二分法,在幾百次提交中快速找出「是從哪一次開始壞掉的」。

(二)平行:分支(branch)與合併(merge)

想像專案的主線叫做 main,是「目前可以正式使用的版本」。要開發新功能時,不是直接改主線,而是從主線開出一條分支,在自己的平行世界裡慢慢做;做好、檢查過了,再合併回主線。

分支到底是什麼?出乎意料地簡單:分支只是貼在某個提交上的一張標籤。開一條新分支,只是多貼一張貼紙;在分支上提交,只有這張貼紙會跟著往前移。

如果兩個人改到了同一處,合併時就會出現「衝突」。Git 不會替您亂選,而是把兩種版本都擺出來,請人決定要留哪一個。這看起來麻煩,卻是在避免有人的改動被悄悄蓋掉。衝突時,您會在檔案裡看到像這樣的標記:

第一天:台北
<<<<<<< HEAD          ← 上半:目前這條分支的版本
第二天:台南
=======
第二天:台中(逛夜市)     ← 下半:要合併進來的版本
>>>>>>> day3
第三天:高雄

您只要把它編輯成想要的結果、刪掉這三種標記行,再提交,衝突就解決了。

(三)整合與品質:審閱與自動檢查

合併之前,需要有「關卡」。現代團隊常見的做法是:

  • 合併請求(Pull Request)與程式碼審閱:作者提出「請把我的分支合併進主線」,至少一位同事會看過,留下意見。這同時也是知識傳遞的機會。
  • 持續整合(CI):每次提交後,自動跑一遍測試、檢查格式,沒通過就不能合併。
  • 保護主分支:規定主線不能直接修改,只能透過審閱通過的合併進來。

(四)分散式:每台電腦都是完整的

前面提過,Git 是「分散式」的。實際上,團隊通常會約定一個放在網路上的遠端倉庫(例如 GitHub)當作交換站:您把自己的提交 push 上去,同事用 pull 下載回來。每個人的電腦都保有完整歷史,所以就算遠端出事,也能從任何一台電腦復原。

五、團隊要選一種「工作流程」

光有工具還不夠,團隊還要約定怎麼用。常見的幾種:

流程做法適合
Git Flow設有長期存在的開發分支、發佈分支、修補分支,角色分明有明確版本週期、需同時維護多個版本的產品
GitHub Flow主線隨時可發佈;每個改動開短命分支、審閱後合併持續上線的網站與服務
主幹開發(Trunk-based)大家頻繁地、以很小的單位直接整合到主幹,搭配功能開關追求高頻率交付、自動化程度高的團隊

沒有哪一種是標準答案。但有一個共通的經驗:分支活得越久,和主線差得越多,合併就越痛。所以許多團隊的取向,是讓分支短一點、改動小一點、更頻繁地整合。

六、規模再大:模組、責任與層層把關

  • 單一倉庫(monorepo)或多倉庫:把所有程式放在同一個倉庫,方便一起修改與重構;或依模組拆成多個倉庫,各自獨立演進。兩者各有取捨,取決於團隊規模與工具支援。
  • 責任歸屬:許多平台支援「程式碼負責人」(例如 GitHub 的 CODEOWNERS),規定某個目錄的改動,必須經過對應的負責人審閱。
  • Linux 核心的層層把關:這個專案本身,就是 Git 誕生的場景。各子系統有自己的維護者,先審閱並收下相關的修改,最後再由上層維護者彙整,逐層往上到托瓦茲。這種「信任鏈」讓一個極大的專案仍能維持品質。

七、版本與發佈

專案要交到使用者手上,需要「版本號」。Git 可以用標籤(tag)把某次提交標示為「v1.2.0」。而業界常用的「語意化版本」規則,是用 主版本.次版本.修補版本 三段數字:不相容的大改動,主版本加一;新增功能且相容,次版本加一;只是修錯誤,修補版本加一。使用者光看版本號,就能約略知道升級的風險。

八、Git 管不了的事

要誠實地說:Git 管的是「程式碼的變動」,管不了「人」。需求有沒有講清楚、團隊有沒有共識、決策為什麼這樣做、文件有沒有人維護,這些仍然要靠溝通與流程,例如問題追蹤系統、設計文件、會議紀錄。工具降低了協作成本,但不能取代共識。

另外,這套思維也不限於寫程式。論文、法規、設計稿、書稿,只要是多人、長時間、反覆修改的工作,「保存歷史、平行發展、審閱後整合、清楚發佈」都用得上。

九、跟著做一遍:用「旅行計畫」學 Git

想像您和朋友正在規劃一趟旅行,計畫寫在一個叫 plan.txt 的檔案裡。我們用 Git 來管理它,一步一步看看發生了什麼事。(指令是在「終端機」裡輸入的;# 後面是說明,不用輸入。)

步驟 1:建立倉庫

mkdir travel && cd travel   # 建立資料夾並走進去
git init                    # 讓 Git 開始管理這個資料夾

資料夾裡多了一個隱藏的 .git,這就是「倉庫」,之後所有的歷史都存在裡面。

步驟 2:第一次提交

先建立 plan.txt,內容是:

第一天:台北
第二天:台中
git status                  # 看狀態:plan.txt 是「未追蹤」
git add plan.txt            # 放進暫存區(回頭看第三節的圖)
git commit -m "建立旅行計畫"   # 蓋章存進倉庫 → 提交 A

步驟 3:開一條分支,加入第三天

git switch -c day3          # 開一條叫 day3 的分支並切過去
# 編輯 plan.txt:把第二天改成「台中(逛夜市)」,再新增一行「第三天:高雄」
git add plan.txt
git commit -m "加第三天,第二天加逛夜市"   # 提交 C(在 day3 上)

步驟 4:回到主線,另一邊也改了同一行

git switch main             # 切回主線
# 編輯 plan.txt:把第二天改成「台南」
git add plan.txt
git commit -m "第二天改去台南"           # 提交 D(在 main 上)

步驟 5:合併,遇到衝突,自己解決

git merge day3              # 把 day3 合併進目前的 main

Git 會告訴您「衝突」:兩邊都改了第二天。打開 plan.txt,就會看到前面說過的那些標記。您把它改成想要的樣子,例如:

第一天:台北
第二天:台南(逛夜市)
第三天:高雄
git add plan.txt            # 告訴 Git「這個衝突我處理好了」
git commit                  # 完成合併 → 合併提交 M

步驟 6:看看歷史

git log --oneline --graph

*   9f3e1a2 (HEAD -> main) Merge branch 'day3'
|\
| * c7d8e9f (day3) 加第三天,第二天加逛夜市
* | b2c4d6e 第二天改去台南
|/
* a1b2c3d 建立旅行計畫

左邊那排星號與線條,就是上面這張圖的文字版。看得懂它,您就看得懂大部分專案的歷史了。

步驟 7:後悔了?

git revert 提交的雜湊值       # 用一個新提交抵銷某次改動(歷史完整保留)

常用指令一覽

指令做什麼
git init在這個資料夾建立一個新倉庫
git status看目前哪些檔案改了、哪些已放進暫存區
git add 檔案把改動放進暫存區
git commit -m "說明"把暫存區的改動存成一個提交
git log --oneline --graph用圖形化的文字看歷史
git switch -c 名稱開一條新分支並切過去
git switch 名稱切換到已有的分支
git merge 名稱把另一條分支合併進目前這條
git revert 雜湊值用新提交抵銷舊提交(安全)
git clone 網址把遠端倉庫整份抓下來
git push / git pull上傳我的提交 / 下載別人的提交
一句話總結:大型專案管理的核心,不是讓每個人更快,而是讓「記憶、平行、整合」三件事的成本都降到團隊負擔得起。Git 用提交、分支與審閱,回答了這三個問題。
